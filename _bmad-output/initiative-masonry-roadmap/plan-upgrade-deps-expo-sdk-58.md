## Intent

**Problem:** The library targets Expo SDK 57 / React Native 0.86 (`version` 57.0.0, lockfile resolving `react-native@0.84.1`, `typescript@5.9.3` where `package.json` declares `7.0.2`). Expo SDK 58 is current and ships React Native 0.88.1 with React 19.3.x, so the toolchain and the documented support window are one SDK behind, and `@types/react-native` (a deprecated stub) still sits in `devDependencies`.

**Approach:** Align the dev toolchain with what SDK 58 ships, keep the published peer window unchanged, and record the new window the way this repo already records an SDK bump: a version bump to 58.0.0, a CHANGELOG entry, and an `expo-sdk-58-compat` capability spec superseding the SDK 57 one. No runtime source changes — the library imports only `react` and `react-native`.

### Decisions (defaults taken while the human was unavailable; reversible)

- **Peer window unchanged**: `react >=18.0.0 <20.0.0`, `react-native >=0.79.0 <1.0.0` stay as-is, so SDK 55–58 all install warning-free and the release is non-breaking (no `### Breaking` CHANGELOG heading needed).
- **Toolchain-critical dev deps only**: pin the SDK 58 set (`react-native@0.88.1`, `react@19.3.1`, `@types/react@19.3.0`) and take latest-patch within each existing major; no eslint 10, jest 30, or Babel 8 majors — `ts-standard@12` requires `eslint ^8.0.1` and `@typescript-eslint/* ^5`, so those majors would break the lint config.
- **Exact pins**: this task is about dependency ranges, so `devDependencies` move from caret to exact versions per AGENTS.md.

## Implementation Notes (cont.) — what the upgrade actually required

Three surprises turned a config-only bump into a small source change. All are RN 0.88 / TS 6 consequences, not stylistic choices.

1. **`typescript` had to come down, not up.** `7.0.2` was declared at HEAD but never installed (lockfile pinned 5.9.3) because every released `@typescript-eslint/parser` — including the newest, 8.72.1 — caps its peer at `>=4.8.4 <6.1.0`. `npm install` therefore failed with `ERESOLVE` before this change too. Pinned `6.0.3`, the newest version inside the ceiling. Revisit when typescript-eslint ships a TS 7 compatible release.
2. **tsconfig modernised for TS 6**: `moduleResolution: "node"` is `node10` and now *errors* (TS5107) — set to `"bundler"`, matching `@react-native/typescript-config@0.88.1`. `lib` went `ES2018` → `ES2019`: `src/ExpoMasonryLayout.tsx` calls `Array.prototype.flatMap`, and once the SDK 57 dependency set was replaced `tsc` reported TS2550 for it under `lib: ES2018`. The baseline built green with the same source and the same `lib` value; the likely reason is that the auto-included `@types/react-native@0.73` stub pulled in broader lib declarations — **unverified**, so record it as a property of the old tree rather than a proven cause.
3. **RN 0.88 dropped the generic parameter from the VirtualizedList types.** `VirtualizedListProps<ItemT>` is now a non-generic intersection re-exported from `@react-native/virtualized-lists`, and the component itself is no longer generic, so both `VirtualizedListProps<MasonryRowData>` (`src/types.ts`) and `useRef<VirtualizedList<any>>` (`src/ExpoMasonryLayout.tsx`) stopped compiling.
   - Public props now derive from `React.ComponentProps<typeof VirtualizedList>`. Deliberate: the emitted `lib/types.d.ts` must stay valid for consumers on RN 0.79–0.87, where `VirtualizedListProps<ItemT>` is generic **without a default** — writing it bare would break their typecheck, and writing it with an argument breaks RN 0.88. `ComponentProps<typeof …>` sidesteps the flip. Verified by typechecking a consumer against RN 0.79 + `@types/react` 19 + TS 5.9.3 (see Verification).
   - The internal ref uses RN 0.88's exported `VirtualizedListInstance`; it never reaches the emitted declarations, so old consumers are unaffected.

Docs: added `docs/specs/expo-sdk-58-compat/spec.md`, marked the SDK 57 spec superseded (and the SDK 55 pointer), added the CHANGELOG `## [58.0.0]` entry with no `### Breaking` heading since the peer window did not move. README needed no change — it documents props, not SDK versions.

Environment notes for future runs in this sandbox: `npm test` needs `--no-watchman` (watchman cannot write `~/.local/state/watchman`) and `npm run lint` needs `XDG_CACHE_HOME` in a writable dir (ts-standard writes `~/.cache/ts-standard`).
